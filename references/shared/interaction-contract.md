# Interaction Contract

> 多阶段 skill 的用户可见骨架要稳定可复用。激活、路由、回执、菜单各有固定职责，不在各模式 README 里各写一套。

## 激活标识

进入任一模式后先输出：

```text
🔥 auto-dev-team - [模式名] 已激活
```

## 路由标识

进入具体模式或发生层级切换时，显式输出：

```text
🧭 路由命中: [模式名 / 当前层级]
```

常见示例：

- `🧭 路由命中: Resume`
- `🧭 路由命中: Architect -> phase`
- `🧭 路由命中: Step`

## 需求确认与澄清闸门

所有写入意图在进入具体写入模式执行前，必须先完成两段强制闸门：

1. `需求确认`：和用户对齐“这次到底要做什么”。
2. `需求澄清问题包`：问几个会影响后续 plan / 执行细节的问题，并强制停下来等用户回复。

它们不是方案设计，也不是 Blast Radius。AI 不能把自己生成的复述当成用户确认，不能在输出问题包后继续自顾自 plan 或写代码。

适用场景：

- 新的写入请求、修复请求、测试生成、清理、重构、优化
- “帮我改一下 / 调整一下 / 修改一下”等写入意图兜底
- Architect 小改动自动转 FastTrack 前
- Resume 后发现用户目标已变化
- 执行中用户补充内容导致目标、边界或验收标准变化

### Phase A: 需求确认

```text
🧾 需求确认
我和你确认一下，这次要做的是：
- 目标: [一句话说明用户真正要达成的结果]
- 本次会改: [预计触碰的功能 / 文件 / 行为类型；未知则写“待定位”]
- 本次不做: [明确排除项；没有则写“暂未发现额外范围”]
- 验收标准: [用户可确认的完成标准；不清楚则列“待确认”]
- 推荐模式: [FastTrack / Architect / Debug / Tester / ...]，因为 [一句话理由]

📌 下一步:
[1] 确认 - 进入需求澄清问题包；不会开始 plan / 写代码
[2] 补充 / 修正 - 调整目标、边界或验收标准
[0] 取消
```

### Phase B: 需求澄清问题包

用户确认 Phase A 后，必须输出：

```text
🧾 需求澄清问题包
为了接下来 plan 不跑偏，请先确认这几个细节：

1. [影响目标文件 / 行为边界 / 验收方式 / 风险取舍的问题]
2. [影响实现策略的问题]
3. [影响测试或验收的问题]

⏸️ Gate: 等你回复后，我才会进入 plan / write-preflight / FastTrack / 执行。
```

问题数量：

- 默认 2-5 个高信号问题。
- FastTrack / Hotfix 可以压缩到 1-3 个，但不能为 0。
- 如果用户已经在原始请求里提供了全部信息，也必须至少问 1 个确认性问题，用来让用户显式确认关键细节。

执行规则：

- Phase A 必须等用户确认后，才允许进入 Phase B。
- Phase B 输出后，当前回合必须停下等待用户回复；禁止继续 plan、禁止进入写入前置、禁止快照、禁止 Blast Radius、禁止代码写入。
- 用户回答 Phase B 后，AI 必须先总结已确认细节；仍有缺口则继续问增量问题包，缺口闭合后才允许进入 plan / write-preflight / 执行。
- 如果用户本轮已明确说“直接执行 / 不用确认 / 信任模式”，仍不能跳过 Phase A 或 Phase B；只能压缩说明和问题数量。
- 如果确认或澄清中出现任何 `待确认` 项，不能进入 FastTrack 直接执行；必须先让用户补充，或切到 Brainstorm / Architect。
- 如果用户回复自然语言修正，以修正后的真实意图为准，不强迫用户回复编号。

## 回执骨架

阶段型输出默认包含：

```text
🧾 阶段回执
📍 当前: [当前状态]
📌 下一步:
[1] ...
[0] ...
```

- `🧾` 负责告诉用户“这一段输出是阶段结果，不是闲聊”
- `📍 当前:` 负责一句话说明现在在哪
- `📌 下一步:` 负责给出可执行分叉
- 编号菜单的具体规则以 `references/shared/menu-contract.md` 为准

## 强制规则

- 激活标识之后，尽快给出一次路由标识，避免用户不知道当前处于哪一层
- 自动升级或降级层级时，必须说明为什么从 `flow` 进入了 `phase / milestone / project`
- 同一类回执只保留一套共享骨架；模式 README 只引用，不重复发明
