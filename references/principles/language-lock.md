# 使用语言：术语锁契约

> 涉及架构、模块归属、接口设计、抽象、重构、测试落层或会诊时，先收紧语言。词一漂，方案就会漂。

## 何时读取

- Survey 项目结构、技术债、抽象机会时
- Brainstorm 里用户开始用 `组件 / 服务 / API / 边界 / 抽象` 描述技术范围时
- Architect 判断功能归属、模块策略、接口面、测试等级时
- FastTrack / Hotfix / Debug 判断修复层级、止血接缝、同型扩散时
- Refactor / Optimize / Cleanup 判断重构方案、抽象机会、删除范围时
- Tester / Step / BDD / GUI 验收判断测试落层、测试面、增量可测产出时
- Resume 复述或恢复已有计划中的模块策略、接口面、测试面时
- Critique / Quality Review 审查结构、复用、抽象、系统性修复时

## 核心术语

| 术语 | 定义 | 使用要求 |
|------|------|----------|
| 模块 | 任何同时有“接口面”和“实现”的代码单元，可以是函数、类、包、目录、跨层业务切片。 | 架构讨论默认说“模块”，不要把 `component`、`service`、`API` 直接当成架构概念。 |
| 接口面 | 调用方和测试必须知道的一切，不只是类型签名。包含参数、返回、错误模式、顺序要求、配置、权限、副作用、幂等、并发、事务/一致性、性能和观测信号。 | 说“改接口”时必须说明改的是哪一部分接口面。 |
| 实现 | 模块内部如何完成行为的代码和私有协作。 | 测试和调用方不应依赖实现细节，除非这是明确暴露的接口面。 |
| 深度 | 模块的接口面能撬动多少行为。深模块是“小接口面承载多行为”，浅模块是“接口面几乎和实现一样复杂”。 | 不用代码行数衡量深度；用调用方要懂的事实是否减少来判断。 |
| 接缝 | 接口面所在的位置，也是行为可以被替换、隔离或观测的位置。 | 架构语境优先说“接缝”，不要泛泛说“边界”。 |
| 适配器 | 落在接缝上、满足接口面的具体实现。 | 说明它是生产适配器、内存适配器、mock 适配器，还是本地替身。 |
| 杠杆 | 调用方、测试和后续改动从模块深度中获得的收益。 | 方案收益要说明是调用杠杆、测试杠杆还是变更杠杆。 |
| 局部性 | 变更、bug、知识和验证是否集中在一个地方。 | 架构候选必须说明它如何提高变更局部性、缺陷局部性、知识局部性或验证局部性。 |
| 契约 | 模块对调用方、数据、环境或用户可见行为的稳定承诺。可以显式，也可以是历史调用形成的隐式契约。 | 兼容性判断必须同时检查显式契约和隐式契约。 |
| 测试面 | 测试应该穿过的接口面。 | 接口面就是测试面；优先测试行为结果，不测试实现过程。 |

## 接口面清单

设计、改动或审查接口面时，至少检查：

- 类型签名：参数、返回、错误结构
- 业务不变量：调用前后必须成立的规则
- 顺序要求：是否必须先初始化、先鉴权、先保存
- 错误模式：异常、错误码、空值、重试语义
- 配置与环境：环境变量、feature flag、运行时依赖
- 权限与身份：谁能调用、以什么角色调用
- 副作用：写库、发请求、发事件、写文件、改缓存
- 幂等与并发：重复调用、并发调用、乱序调用的语义
- 事务与一致性：哪些状态必须一起成功或一起失败
- 性能承诺：复杂度、超时、批量规模、资源占用
- 观测信号：日志、trace、事件、指标、可诊断输出

## 接缝状态

判断是否要新增或移动接缝时，先标清状态：

- 现有接缝：仓库里已经有调用方或测试穿过它
- 候选接缝：为了加深模块或隔离依赖而提出，但还未证明必要
- 内部接缝：只服务模块内部实现或内部测试，不暴露给外部调用方
- 外部接缝：调用方、测试或其他系统真实穿过的接口面
- 偶然接缝：因为目录、文件、框架分层而形成，但没有清晰契约

只有在至少两个具体适配器、可替换依赖、测试替身、部署差异或清晰所有权差异存在时，才把候选接缝升级为外部接缝。否则优先保持内部接缝，避免制造空转抽象。

## 适配器类型

| 类型 | 定义 | 测试策略 |
|------|------|----------|
| 生产适配器 | 真实运行时使用的实现，如 HTTP、数据库、队列、第三方 SDK。 | 通过集成 / 契约 / smoke 覆盖关键行为。 |
| 内存适配器 | 用内存数据结构满足同一接口面。 | 用于快速测试业务行为和状态流转。 |
| Mock 适配器 | 为不可控外部系统提供的测试替身。 | 只模拟必要契约，不复制第三方实现。 |
| 本地替身 | PGLite、临时文件系统、本地队列等可在测试内运行的替代依赖。 | 优先用于验证更接近真实行为的接口面。 |

## 深度判断

一个重构或新模块更“深”，通常会出现这些信号：

- 调用方需要知道的事实变少
- 多处调用方的编排逻辑被集中到一个模块
- 测试可以穿过同一个接口面覆盖更多行为
- 内部实现变化时，调用方和测试不需要跟着改
- 删除该模块后，复杂度会重新扩散到多个调用方
- 错误处理、幂等、权限、事务等规则更集中

反过来，如果一个模块只是转发参数、复制命名、包一层同等复杂的接口面，它很可能是浅模块。

## 禁用词翻译

这些词不是不能出现，而是不能停在模糊层。出现时必须翻译成术语锁语言：

| 模糊词 | 必须追问或改写成 |
|--------|------------------|
| 组件 | 是 UI 组件、模块、适配器，还是框架 artifact？ |
| 服务 | 是进程、远端依赖、业务模块、生产适配器，还是目录命名？ |
| API | 是 HTTP endpoint、类型签名、完整接口面，还是第三方接口？ |
| 边界 | 是用户需求范围、业务边界、DDD bounded context，还是架构接缝？ |
| 抽象 | 是加深模块、收窄接口面、提取共享实现，还是新增接缝？ |
| 工具函数 | 它是否有独立接口面和杠杆，还是只是实现细节？ |
| 平台级 | 是共享模块、机制模块、运行时设施，还是跨域政策？ |

## 输出纪律

- 架构建议必须同时说清：涉及哪些模块、哪个接口面、接缝在哪里、实现隐藏什么、收益体现在哪类杠杆和局部性。
- 测试建议必须说清：测试穿过哪个接口面，覆盖哪些契约，哪些实现细节不测。
- 重构建议必须说清：是加深现有模块、移动接缝、引入适配器，还是只清理实现。
- 会诊和质量复核必须检查：术语是否漂移，`组件 / 服务 / API / 边界 / 抽象` 是否已经被翻译成精确术语。
- 不为了术语统一而强行重命名文件、类、目录或业务词；术语锁约束的是分析与方案语言，代码命名仍优先服从项目现有约定。
