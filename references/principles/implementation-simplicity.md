# 实现简洁原则

> 在不牺牲安全、验证和正确性的前提下，用最少的新东西完成当前任务。

## 何时读取

- 开始实际实现代码、测试或配置改动前。
- 需要判断复用、依赖、新文件、新抽象或模块归属时。
- 质量复核发现实现膨胀、重复、过早抽象或依赖增加时。

## 优先级

实现简洁服从 AutoDevTeam 的全局优先级：

```text
安全 / 可回退
> 增量可测
> 正确
> 简洁
> 速度
```

因此不得为了少写代码而跳过错误处理、权限边界、数据保护、测试、观测验证或必要的兼容处理。

## 实现阶梯

动手前按顺序回答，只有上一层不能满足当前验收时，才进入下一层。

1. 不做：这个改动是否真的属于本任务验收？若不是，停下来问用户或标为 Not In Scope。
2. 复用现有实现：项目里是否已有模块、函数、适配器、测试工具或脚本能覆盖？
3. 使用平台原生能力：语言标准库、浏览器 API、框架内置能力、数据库/运行时原生命令是否足够？
4. 使用已有依赖：仓库已安装依赖是否已经提供该能力？
5. 局部实现：能否把改动融入现有模块和接口面，而不是新建平行模块？
6. 新建抽象：只有重复达到 3 次以上，或接口面会明显变简单，才新增共享抽象。
7. 新增依赖：只有安全、维护、体积、许可证和现有替代方案都评估通过，才考虑引入。

## 执行前自检

- 新文件：是否真的有独立职责？能否放进现有模块？
- 新 helper / wrapper：是否只是转发一行已有 API？若是，删除或内联。
- 新配置：是否已有默认值、环境变量或框架约定可复用？
- 新依赖：是否能被标准库、平台原生能力或已有依赖替代？
- 新抽象：是否满足 Rule of Three，且接口面更简单？
- 新测试工具：是否能复用现有 test helper、fixture、factory 或 GUI 脚本？

## 执行后复核

质量复核时追加检查：

- 是否新增了 PM / 用户未要求的能力。
- 是否把 1-2 次使用提前抽成共享层。
- 是否产生了平行模块、平行配置或平行测试工具。
- 是否有一眼可删的 wrapper、adapter、helper、mapper 或 constants 文件。
- 是否因为追求“架构完整”增加了验证负担。
- 删除或合并后，后台测试、观测验证和 GUI 验收是否仍然成立。

## 输出回执

当该原则影响方案时，在计划、会诊或质量复核里给出简短回执：

```text
🧱 实现简洁检查
- 复用: [复用了什么 / 未找到可复用项]
- 原生能力: [使用 / 不适用，原因]
- 新增抽象: [无 / 必要，原因]
- 新增依赖: [无 / 必要，原因]
- 结论: [按最小实现继续 / 需要收窄方案 / 需要升级模式]
```
